提示词不是一次写成的——好的提示词是"调试"出来的。以下是 2026 年业界最实用的调试方法：

### 12.6.1 从简单开始

不要一上来就写五要素完整的复杂提示词。从最短的提示词开始，测试 AI 是否能理解基本意图。如果能，再逐步加约束和格式要求。这样你能知道"是哪一步出了问题"。

### 12.6.2 一次只改一个变量

当你调试提示词时，每次只改一个东西——改角色、改约束、改示例顺序。如果一次改三个，效果好或坏你都不知道是谁的功劳。这是科学实验的基本原则，也是提示词调试的黄金法则。

### 12.6.3 记录版本

给每个提示词版本编号，记录改动内容和效果。推荐用 Git 管理提示词，就像管理代码一样。

```
v1.0: "总结这篇文章" -> 输出太长，缺少重点
v1.1: +"用三句话总结" -> 长度合适，但有时超过三句
v1.2: +"每句话不超过30字" -> 输出稳定，符合预期
v2.0: +角色设定 -> 总结风格更专业
```

### 12.6.4 A/B 测试

对同一个任务准备两个不同版本的提示词，用同一批 20-50 个测试用例分别跑一遍，比较结果。A/B 测试是验证"提示词改得好不好"的唯一可靠方法。主观感觉不可靠——你觉得自己改得好，数据可能说相反。

### 12.6.5 常见错误模式

| 错误模式 | 表现 | 修复方法 |
|---------|------|---------|
| 提示词太长 | AI 忽略后面的指令 | 精简约束，控制在 500 字以内 |
| 约束冲突 | "详细展开" + "不超过 50 字" | 检查约束之间是否矛盾 |
| 示例与任务不符 | AI 模仿示例而非执行任务 | 确保示例与目标任务的模式一致 |
| 角色过于宽泛 | "你是一个专家" | 改为"你是一个刑法律师，专注于..." |
| 负面指令过多 | AI 反而更关注"不要"的内容 | 多用正面指令说"要什么"，少用"不要什么" |

### 12.6.6 2026 年的系统性方法

提示词调试已经从"凭感觉改"进化到"系统化工程"。核心方法论：

**从"手工调参"到"结构化约束"**：2024 年以前，提示词工程是"手工艺"——靠个人经验和直觉。2025-2026 年，趋势是让提示词"结构化"：用 XML 标签、JSON Schema、Markdown 标题等结构化语法组织提示词，减少歧义，提高可复现性。

**System Prompt 工程化**：2026 年，产品级 AI 应用把核心提示词逻辑放在系统提示词（System Prompt）中，用户看不到。系统提示词不再是"一段话"，而是经过版本管理、A/B 测试、自动化回归测试的"工程资产"。优秀的系统提示词可能经过数百次迭代，每次迭代都有数据支撑。

**提示词优化工具**：不再手动调试。DSPy（斯坦福 2024 年开源）让你定义"输入是什么、输出是什么、怎么评判好坏"，它自动搜索最优提示词。类似工具还有 Promptim（Anthropic）、Prompt Poet（Character.AI）。2026 年，提示词优化正在从"手艺"变成"科学"。
