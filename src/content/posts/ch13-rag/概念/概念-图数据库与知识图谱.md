## 一句话理解

图数据库（Graph Database）和知识图谱（Knowledge Graph）是两种紧密相关但不同的概念：**图数据库存储实体-关系-实体的三元组，是一种数据存储技术；知识图谱是结构化的知识网络，是一种知识表示方法**。图数据库是实现知识图谱的底层基础设施之一，而知识图谱是图数据库在知识管理领域的上层应用。

> 类比：图数据库是"书架"（存储工具），知识图谱是"百科全书"（知识内容）。你可以用不同的书架来放百科全书，也可以用同一个书架放其他类型的书。

## 核心概念

### 1. 节点、边、属性（Node, Edge, Property）

图数据库的三个基本元素：

```
节点 (Node) ──── 边 (Edge) ──── 节点 (Node)
    │                               │
    └── 属性 (Property)             └── 属性 (Property)
```

- **节点（Node/Vertex）**：表示实体，如"人物"、"公司"、"概念"
- **边（Edge/Relationship）**：表示实体之间的关系，如"任职于"、"收购"、"属于"
- **属性（Property）**：节点和边的附加信息，如人物的"年龄"、关系的"开始时间"

### 2. 三元组（Triple）

三元组是知识图谱的最小单元，格式为 `(头实体, 关系, 尾实体)`：

| 头实体 (Head) | 关系 (Relation) | 尾实体 (Tail) |
|:---|:---|:---|
| Claude | created_by | Anthropic |
| Anthropic | headquartered_in | San Francisco |
| San Francisco | located_in | California |
| [[概念-Transformer]] | is_basis_of | [[概念-LLM概述]] |
| [[概念-RAG]] | uses | [[概念-向量数据库]] |

### 3. 本体（Ontology）

本体定义了知识图谱中的**实体类型、关系类型和约束规则**。它是知识图谱的"schema"——规定什么样的实体可以有什么样的关系。

```
本体示例（企业知识图谱）:

实体类型: Person, Company, Product, Location, Event
关系类型: works_at(Person→Company), produces(Company→Product),
          located_in(Company→Location), attends(Person→Event)
约束: works_at 只能从 Person 指向 Company
```

## 图数据库 vs 向量数据库

这是 AI 应用开发中最常见的架构选择问题：

| 维度 | 图数据库（Graph DB） | 向量数据库（Vector DB） |
|------|---------------------|------------------------|
| 核心能力 | 管理关系 | 管理相似度 |
| 数据结构 | 图（节点+边） | 向量（高维空间中的点） |
| 查询方式 | 图遍历（Cypher, SPARQL） | 相似度搜索（ANN） |
| 擅长回答 | "A 和 B 有什么关系？" | "哪些内容与 X 相似？" |
| 典型查询 | "查找所有与X有直接关系的人" | "查找与问题语义最相关的文档" |
| 推理能力 | 支持多跳推理（A→B→C→D） | 不支持推理，只做匹配 |
| 代表产品 | Neo4j, Amazon Neptune, ArangoDB | Pinecone, Milvus, Weaviate, Qdrant |
| 在 RAG 中的角色 | Graph RAG（结构化知识检索） | Vector RAG（语义相似度检索） |
| 典型场景 | 社交网络、推荐系统、欺诈检测 | 文档检索、语义搜索、相似商品推荐 |

### 关键洞察：图管关系，向量管相似

```
用户问题: "推荐与Claude类似的AI模型"

向量数据库路径：
  查询 "Claude AI model" → 向量相似度 → 返回语义相似的模型列表

图数据库路径：
  节点 Claude → [competitor_of] → GPT → [competitor_of] → Gemini
  节点 Claude → [same_category] → LLM → [members] → [GPT, Gemini, Llama]
```

两者不冲突，而是互补。在 Graph RAG 中，图数据库提供结构化关系，向量数据库提供语义相似度，两者结合效果最好。

## 知识图谱在 AI 中的应用

| 应用场景 | 说明 | 图数据库角色 |
|---------|------|-------------|
| Graph RAG | 从知识图谱中检索实体和关系，增强 LLM 回答 | 结构化知识源 |
| 实体链接（Entity Linking） | 将文本中的提及（mention）链接到知识图谱中的实体 | 实体消歧和归一化 |
| 多跳问答（Multi-hop QA） | 需要多步推理的问题（如"X的创始人的妻子的公司叫什么"） | 关系推理引擎 |
| 推荐系统 | 基于用户-物品-属性的关系图进行推荐 | 关系图谱 |
| 反欺诈 | 通过关系图谱发现异常关联模式 | 异常检测 |
| 对话系统 | 维护对话中的实体状态和关系 | 对话状态追踪 |

## 2026 年：Graph RAG 让图数据库和向量数据库互补

2025-2026 年，Graph RAG 成为 RAG 领域的重要方向。其核心思想是：

```
传统 RAG:
  用户问题 → 向量检索 → 相关文档块 → LLM 生成回答

Graph RAG:
  用户问题 → 实体识别 → 图数据库检索实体+关系 → 向量检索补充语义内容
           → 融合结果 → LLM 生成回答
```

Graph RAG 特别适合需要**结构化推理**的场景（如"比较两家公司的供应链"），而传统 Vector RAG 更适合**语义匹配**场景（如"找一篇关于 AI 安全的文章"）。
